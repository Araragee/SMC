## Remaining Opportunities (Not Yet Fixed)

### A. `session_checker_task` — no HTTP 409 surface to the frontend for stale-version conflicts

**Context:** The backend correctly returns HTTP 409 when a client sends a stale `version`. However, none of the views that call schedule store actions have error handling that specifically catches `status === 409` and shows the user a "session was updated by someone else, please reload" message. Users currently see a generic error toast.

**Suggested fix:** In `SessionDetailModal.vue` (and any view that calls store actions), intercept `axios` errors with `err.response?.status === 409` and display a user-friendly conflict message prompting a page/session refresh.

---

### B. `session_checker_task` — off-hours back-off applies to stale reminders too

**Context:** The 5-minute back-off during 00:00–06:00 UTC now also throttles the newly-unblocked stale-reminder check. In most deployments this is fine, but schools operating across time zones could miss a reminder window overnight.

**Suggested fix:** If cross-timezone operation becomes a concern, use a separate `sleep_interval` for the stale block or move it to a dedicated task.

---

### C. `AdminPayments.vue` — no pagination, fetches up to 500 records client-side

**Context:** The admin Ledger page loads up to 500 payments at once and filters client-side. For schools with heavy payment volume this becomes sluggish.

**Suggested fix:** Add server-side pagination (skip/limit params are already supported in the backend) and update the frontend to page through results.

---

### D. `create_recurring_sessions` — no rollback on partial conflict

**Context:** With the overlap check now in place, if occurrence 7 of a 10-occurrence series conflicts, the endpoint raises 409 and SQLAlchemy rolls back. However, the error message says "Session #X conflicts" but doesn't tell the admin which date the conflicting occurrence falls on.

**Suggested fix:** Format the 409 detail with the actual date string: `f"Scheduling conflict on {format_dt(occurrence_start)}: the {role} already has an active session overlapping this slot."` This gives the admin enough information to either adjust the skip_dates list or resolve the conflict.

---

### E. `backend/routers/users.py` — no rate-limiting on `POST /users/` (admin-only)

**Context:** Admin-only routes are generally safe, but there is no per-IP or per-user rate limit on bulk user creation. An attacker who compromises an admin token could create thousands of accounts rapidly.

**Suggested fix:** Apply a conservative `@limiter.limit("30/minute")` decorator on `create_user`, consistent with the existing login endpoint's `10/minute` policy.

## 🔴 High-Priority Bugs

### 2. N+1 Queries on All Session Mutation Endpoints

`backend/routers/sessions.py` defines `_session_eager_options()` (line 77) which bulk-loads `proofs`, `homeworks`, and `instrument` in one pass. This is correctly applied to all **list/fetch** queries.

However, every **mutation** endpoint (approve, reject, counter, complete, upload-proof, etc.) fetches the session like this:

```python
db_session = db.query(models.Session).filter(models.Session.id == session_id).first()
# ... mutate ...
db.commit()
db.refresh(db_session)  # ← resets lazy state
return map_session(db_session)  # ← map_session accesses .proofs → lazy load hit
```

`db.refresh()` after commit expires all attributes, so `map_session()`'s access to `db_session.proofs` triggers a separate SELECT per session. On busy endpoints (admin approving many sessions) this becomes one extra query per response.

**Fix:** apply eager options on the initial fetch:
```python
db_session = (
    db.query(models.Session)
    .options(*_session_eager_options())
    .filter(models.Session.id == session_id)
    .first()
)
```
Then reload after commit with the same options, or expunge and re-query.

Affected functions: `update_session`, `approve_session_as_teacher`, `reject_session_as_teacher`, `counter_session_as_teacher`, `counter_session_as_student`, `approve_session_as_student`, `approve_session_as_admin`, `reject_session_as_admin`, `complete_session_as_admin`, `upload_session_proof`, `reject_session_proof`, and ~8 others.

### 3. Missing DB Rollback on Commit Failures

`backend/routers/sessions.py` has 27 `db.commit()` calls. Only **one** is wrapped in a try/except with a `db.rollback()`. All others silently leave the session in a dirty state if the commit fails (e.g., a DB constraint violation mid-transaction).

**Fix pattern:**
```python
try:
    db.commit()
    db.refresh(db_session)
except Exception:
    db.rollback()
    raise HTTPException(status_code=500, detail="Database error, please retry.")
```

This pattern should be standardized, ideally via a context manager utility.

### 4. "Amount (USD)" Label — Wrong Currency

`frontend/src/views/admin/Payments.vue` lines 495 and 602 label the amount field as `Amount (USD) *`. The actual currency displayed throughout the app is `PHP` (Philippine Peso, `en-PH` locale). This is a confusing mislabel.

### 5. Cart Persists Across Logouts

`frontend/src/stores/shop.ts` initializes the cart from `localStorage.getItem('smc_cart')` and saves it back on every change. If a student logs out and a different account logs in on the same browser, they will see the previous user's cart items. This is both a UX bug and a minor privacy concern.

**Fix:** Clear the cart key in `localStorage` during the auth store's logout action:
```ts
// in auth.ts logout()
localStorage.removeItem('smc_cart')
```

### 6. `ActivityLog` FK Has No `ondelete` Cascade

`backend/alembic/versions/f3a1b2c4d5e6_add_activity_logs_table.py` defines:
```python
sa.Column('actor_id', sa.Integer(), sa.ForeignKey('users.id'), nullable=True),
```

No `ondelete` clause is set. If an admin hard-deletes a user, SQLite will enforce the FK constraint and prevent the delete (or silently ignore it depending on pragma settings). The intent is clearly for `actor_id` to become `NULL` when the actor is deleted.

**Fix:** Add `ondelete="SET NULL"` to the FK:
```python
sa.ForeignKey('users.id', ondelete="SET NULL")
```
Requires a new Alembic migration to `DROP` and re-`ADD` the column (SQLite limitation).

### 7. New Sessions Created With `version = NULL`

`propose_session_as_student` and `propose_session_as_teacher` create `models.Session(...)` without setting `version`. The column defaults to `NULL`, not `0`. The first time `_bump_version` runs on the session it sets `version = (None or 0) + 1 = 1`, which is fine. However, `_check_version` compares the client-sent `expected` against `db_session.version`. If a client reads a freshly-proposed session and sees `version=null`, then sends back `version=null` on the next action, `_check_version` will pass even if a concurrent edit snuck in.

**Fix:** Set `version=0` explicitly when constructing new sessions:
```python
db_session = models.Session(..., version=0)
```

## 🟢 Low-Priority / Polish

### 8. `console.error` Calls in Production Stores

The following stores use bare `console.error(err)` for error handling: `shop.ts`, `schedule.ts`, `interactions.ts`, `notification.ts`. These are fine during development but leak stack traces in production. Consider a thin `logger` wrapper that no-ops in production builds or forwards to an error tracking service.

### 9. Refresh Token Cleanup on User Deletion

`RefreshToken` model has a FK to `users.id` but no cascade. Deleting a user leaves orphaned refresh tokens in the `refresh_tokens` table. The auth overhaul migration (`b8c1e3f4d6a2`) doesn't set `ondelete`. 

**Fix:** Add `ondelete="CASCADE"` to the FK so tokens are cleaned up automatically.

### 10. `_seed_defaults()` Runs on Every App Restart

The startup lifespan hook always calls `_seed_defaults()`, which opens a DB connection and runs 3 SELECTs + potential INSERTs on every process start. While idempotent, this adds latency to cold starts and is fragile if the DB is temporarily unavailable at boot.

**Recommendation:** Gate it behind an environment variable (`SEED_ON_BOOT=true`, off by default in production) or move the admin-user creation to an explicit Alembic data migration.

### 11. Deactivated Users Still Appear in Session History

`backend/routers/users.py` soft-deletes users by setting `is_active = False` and filters them out of user-list queries. However, the sessions router fetches participants by ID directly, so deactivated users will still appear as `teacher_id` / `student_id` on old sessions — which is correct for history, but the user detail (name, email) may no longer be accessible via the users API. The frontend should handle the case where `teacher.name` or `student.name` is missing on a session gracefully.
